# Сервис бронирования переговорных комнат — микросервисная архитектура

Система бронирования переговорных комнат в production-стиле, построенная на Go, PostgreSQL и Docker Compose.

## Обзор архитектуры

Система состоит из 6 микросервисов за единым API Gateway, доступным по адресу `localhost:8080`.

```text
┌─────────────────────────────────────────────────────────────┐
│                    API Gateway (:8080)                     │
│  Проверка JWT · Ролевой доступ · Обратный прокси          │
└────┬──────────┬──────────────┬──────────────┬───────────────┘
     │          │              │              │
┌────▼───┐ ┌───▼────┐  ┌──────▼──────┐  ┌───▼──────┐
│  Auth  │ │  Room  │  │Availability │  │ Booking  │
│Service │ │Service │  │  Service    │  │ Service  │
│(:8081) │ │(:8082) │  │  (:8083)    │  │ (:8084)  │
│auth_db │ │room_db │  │avail_db     │  │booking_db│
└────────┘ └────────┘  └─────────────┘  └────┬─────┘
                                             │
                                      ┌──────▼──────┐
                                      │ Conference  │
                                      │ Mock Service│
                                      │  (:8085)    │
                                      └─────────────┘
```

## Почему выбрана такая декомпозиция

Каждый сервис владеет одним ограниченным контекстом и своей собственной базой данных:

- **auth-service** — идентификация пользователей и выпуск JWT. Вынесен отдельно, потому что аутентификация — это сквозная задача со своими требованиями к безопасности. Хранит приватный JWT-ключ; все остальные сервисы используют публичный ключ для валидации.

- **room-service** — CRUD-операции для комнат. Это простое управление ресурсами, которое меняется редко. Выделение в отдельный сервис позволяет не связывать изменения метаданных комнат с логикой бронирования или доступности.

- **availability-service** — расписания, генерация слотов и статусы доступности слотов. Это **источник истины** о том, свободен слот или уже забронирован. Хранение статуса слота здесь (а не в booking-service) означает, что самый горячий endpoint (`/rooms/{roomId}/slots/list`) читает напрямую из одной базы данных без межсервисных вызовов.

- **booking-service** — жизненный цикл бронирования (создание, отмена, список). Оркестрирует процесс бронирования: вызывает availability-service для атомарного бронирования/освобождения слотов, после чего сохраняет записи о бронировании в своей собственной базе данных.

- **conference-mock-service** — имитирует внешнего поставщика ссылок для конференций. Полностью stateless с хранилищем идемпотентности в памяти. Изолирован отдельно, чтобы его сбои не влияли на основной поток бронирования.

## Ключевые проектные решения

### Почему слоты генерируются заранее (на 30 дней вперед)

Слоты имеют **стабильные UUID, сохраненные в базе данных**. Это дает:

1. **Быстрое чтение** — самый горячий endpoint читает заранее проиндексированные строки вместо вычисления на лету.
2. **Атомарное бронирование** — `SELECT ... FOR UPDATE` по реальной строке вместе с exclusion constraint предотвращает двойное бронирование на уровне базы данных.
3. **Ссылочную целостность** — бронирования ссылаются на реальные ID слотов.

Фоновый worker ежедневно расширяет окно слотов, чтобы горизонт в 30 дней всегда поддерживался.

### Как самый горячий endpoint остается быстрым

`GET /rooms/{roomId}/slots/list?date=YYYY-MM-DD` читает из:

```sql
SELECT ... FROM slots
WHERE room_id = $1 AND start_at >= $2 AND start_at < $3 AND status = 'free'
```

Это поддерживается за счет:
- частичного индекса по `(room_id, start_at) WHERE status = 'free'`
- exclusion constraint `EXCLUDE USING gist (room_id WITH =, tstzrange(start_at, end_at) WITH &&)`
- отсутствия межсервисных вызовов — availability-service является единственным источником истины.

### Защита от двойного бронирования

1. **На уровне базы данных**: `EXCLUDE USING gist` предотвращает пересечение слотов. `UNIQUE(room_id, start_at)` предотвращает дубликаты.
2. **На уровне приложения**: `SELECT ... FOR UPDATE` внутри транзакции гарантирует атомарные переходы статуса.
3. **На уровне бронирования**: частичный уникальный индекс `UNIQUE(slot_id) WHERE status = 'active'` в `booking_db`.

### Идемпотентная отмена

Отмена сначала проверяет текущий статус:
- Если уже `cancelled` → вернуть 200 с текущим состоянием (no-op).
- Если `active` → освободить слот (идемпотентное освобождение), затем обновить статус на `cancelled`.
- Освобождение идемпотентно: `UPDATE ... WHERE id = $1 AND current_booking_id = $2 AND status = 'booked'` — ошибки не будет, даже если слот уже освобожден.

### Аутентификация: /register, /login, /dummyLogin

- `/dummyLogin` всегда возвращает JWT для **фиксированного UUID** на каждую роль (создается при первом вызове).
- `/register` создает реального пользователя с паролем, захешированным через bcrypt, и указанной ролью.
- `/login` аутентифицирует по bcrypt-хешу и возвращает JWT.
- JWT использует **RS256**: auth-service хранит приватный ключ, все остальные сервисы валидируют токен по публичному ключу.
- JWT содержит `user_id` (UUID) и `role` (admin|user).

### Поток создания ссылки на конференцию

Когда `createConferenceLink: true`:

1. Бронирование создается сразу с `conference_status: 'pending'`.
2. Создается запись `conference_jobs`.
3. Фоновый worker опрашивает ожидающие задачи и вызывает conference-mock-service.
4. При успехе: `conference_status → 'ready'`, ссылка сохраняется.
5. При ошибке: повтор с exponential backoff (до 5 попыток), затем `conference_status → 'failed'`.

**Обрабатываемые сценарии отказа:**
- **Сервис конференций недоступен** → worker повторяет попытки с exponential backoff.
- **Успех получен, но booking-service упал до сохранения** → при следующем запуске worker снова вызывает conference service. Mock-сервис идемпотентен по `booking_id`, поэтому возвращается та же ссылка.
- **Бронирование отменено до создания ссылки на конференцию** → worker обнаруживает отмененное бронирование и помечает задачу как `done`, не вызывая внешний сервис.

## Быстрый старт

### Предварительные требования
- Docker и Docker Compose

### Запуск

```bash
make up
```

Это:
1. Запустит PostgreSQL и создаст 4 базы данных
2. Выполнит миграции для всех сервисов
3. Соберет и запустит все 6 сервисов
4. Создаст тестовые учетные записи admin и user
5. Откроет API по адресу `http://localhost:8080`

### Тестовые данные

```bash
make seed
```

Создает фиксированных тестовых пользователей для `/dummyLogin`:
- Admin: `00000000-0000-0000-0000-000000000001`
- User: `00000000-0000-0000-0000-000000000002`

### Остановка

```bash
make down
```

## Тестирование

### Unit-тесты

```bash
make test
```

### Покрытие тестами

```bash
make cover
```

### E2E-тесты

При запущенных сервисах:

```bash
make test-e2e
```

E2E-тесты покрывают:
1. Администратор создает комнату → создает расписание → пользователь получает список слотов → пользователь бронирует слот
2. Пользователь отменяет бронирование → повторная отмена возвращает 200
3. Администратор не может бронировать (403)
4. Расписание неизменяемо (409 при повторном создании)
5. Поток Register + Login

## Допущения

1. **Один экземпляр каждого сервиса** — нет распределенной блокировки для worker'а генерации слотов. Для нескольких реплик понадобились бы pg advisory locks или leader election.
2. **Нет soft delete для комнат** — комнаты нельзя удалить или деактивировать после создания.
3. **Расписание неизменяемо** — его нельзя изменить или удалить после создания.
4. **`/bookings/my`** — только **активные** бронирования, у которых **начало** слота еще не наступило или наступило сейчас (`slot_start_at >= now()`), согласно `api.yaml`.
5. **Conference mock использует хранилище в памяти** — это допустимо для mock-сервиса; в реальной реализации использовалась бы база данных.
6. **Ключи RS256 встроены в репозиторий** — только для локальной разработки. В production они должны управляться через secrets manager.
7. **Все времена в UTC** — логика преобразования часовых поясов отсутствует.
8. **Длительность слота всегда 30 минут** — обеспечивается ограничением `CHECK` на уровне базы данных.
